# Audit Rahayat CMS — 7 September 2026

**Kesimpulan:** CMS memiliki fondasi keamanan dan tampilan responsif yang cukup baik, tetapi belum layak dinyatakan aman untuk menyimpan dokumen pendaftaran nyata sebelum temuan prioritas P1 ditangani. Akses dokumen SPMB tanpa login berhasil direproduksi menggunakan file sintetis. Sanitizer HTML juga terbukti dapat meloloskan atribut eksekusi JavaScript.

Audit meliputi kode PHP, model database, konfigurasi Apache, aset, HTTP lokal, dan browser pada `http://rahayat-cms.test/`. Versi aplikasi dalam konfigurasi: 1.10.0. Lingkungan lokal: PHP 8.5.8 dan Apache 2.4.62 di Windows. Temuan dibedakan antara hasil uji langsung, analisis kode, dan risiko konfigurasi. Tidak dilakukan perubahan kode aplikasi, penggantian akun, pengambilan dokumen pribadi, maupun pengiriman formulir pendaftaran. File uji sintetis telah dihapus. Kunjungan halaman dapat tercatat oleh analitik bawaan CMS.

Laporan diletakkan di `app/audit-reports/` karena folder `app` diblokir oleh konfigurasi document root alternatif proyek; hindari mempublikasikan laporan kerentanan melalui folder publik.

| Area | Penilaian |
| --- | --- |
| Keamanan CMS | Perlu perbaikan segera: sanitizer, API berita, revokasi sesi, dan throttle |
| Keamanan data | Risiko tinggi: bypass dokumen SPMB dan status pendaftaran mudah ditebak |
| Kecepatan akses | Respons HTML lokal cukup cepat; bottleneck konkurensi dan cache perlu dibenahi |
| UI/UX | Beranda/login responsif; aksesibilitas dan konsistensi perilaku perlu diperbaiki |

P1 berarti prioritas sebelum produksi/data nyata; P2 berarti perbaikan siklus berikutnya; P3 berarti penyempurnaan. Ini prioritas teknis, bukan skor CVSS atau sertifikasi keamanan.

## Temuan keamanan CMS dan data

### S1 — P1/Tinggi: dokumen SPMB dapat diakses tanpa login

**Bukti:** `public/index.php:206–245`. Klasifikasi privat dilakukan dengan `str_starts_with($normalizedFile, 'spmb/')` sebelum resolusi path. Segmen `./` tidak dinormalisasi sebelum pemeriksaan. Pemeriksaan `realpath` berikutnya hanya membatasi file tetap berada di storage, sehingga tetap mengizinkan file privat.

Pengujian HTTP tanpa cookie autentikasi, terhadap PDF sintetis yang dibuat khusus audit:

| URL query pada `/index.php` | Hasil |
| --- | --- |
| `?url=storage/spmb/audit-access-probe-20260907.pdf` | 403 |
| `?url=storage/./spmb/audit-access-probe-20260907.pdf` | 200; isi file sintetis terkonfirmasi |
| `?url=storage/SPMB/audit-access-probe-20260907.pdf` | 200 pada filesystem Windows lokal |

Respons bypass juga memuat `Cache-Control: public, max-age=2592000`, sehingga dokumen privat ditandai boleh dicache publik selama 30 hari. Eksploitasi membutuhkan nama/path dokumen diketahui; ini bukan bukti seluruh nama dokumen dapat didaftar. Varian huruf besar bergantung filesystem, sedangkan kesalahan segmen `./` berasal dari logika aplikasi.

Selain bypass anonim, URL normal hanya mengecek keberadaan `user_id`, tanpa peran admin/panitia, izin SPMB, atau status akun aktif. Akun murid/nonpanitia yang mengetahui URL juga tidak ditolak oleh guard ini. Halaman dashboard memiliki pemeriksaan lebih ketat yang tidak diterapkan pada handler file.

**Perbaikan:** gunakan endpoint unduh dokumen berdasarkan ID record; tentukan klasifikasi privat dari path kanonis yang sudah tervalidasi; periksa akun aktif, role, izin SPMB, dan relasi dokumen terhadap record. Terapkan `private, no-store` untuk semua respons privat. Tolak path ambigu dan tempatkan berkas privat terpisah dari aset publik.

**Kriteria selesai:** anonim serta akun nonpanitia ditolak untuk seluruh variasi path; hanya akun berizin dapat mengunduh; tidak ada header cache publik untuk dokumen privat.

### S2 — P1/Tinggi: sanitizer HTML dapat meloloskan stored XSS

**Bukti:** `app/Core/Security.php:317–386`. Saat menemukan tag yang tidak diizinkan, fungsi memindahkan anak tag ke parent lalu melanjutkan ke sibling lama; anak yang dipindahkan tidak diperiksa lagi pada putaran tersebut.

Uji PHP CLI langsung terhadap implementasi asli menggunakan penanda sintetis:

```html
<section><section><img src=x onerror="window.__audit=1"></section></section>
```

Hasil setelah dua kali `Security::sanitizeHtml()`:

```html
<img src="x" onerror="window.__audit=1">
```

Kontrol pembanding `<p><img src=x onerror="window.__audit=1"></p>` dibersihkan dengan benar. Artinya kegagalan spesifik terjadi pada traversal tag pembungkus, bukan seluruh penyaringan.

Alur berita menyaring saat simpan dan saat baca, tetapi payload bersarang dapat bertahan melintasi keduanya. `views/frontend/news/show.php:83` mencetak HTML hasil persiapan langsung. CSP pada `public/index.php` dan `public/.htaccess` mengizinkan `unsafe-inline`, sehingga tidak menjadi penghalang handler inline yang lolos. Dampak potensial adalah JavaScript berjalan dalam origin CMS dan melakukan tindakan memakai sesi korban; HttpOnly tidak mencegah tindakan same-origin tersebut.

**Batas bukti:** bypass sanitizer direproduksi langsung, tetapi payload tidak disimpan ke database dan tidak dieksekusi pada browser pengguna. Eksploitasi stored XSS memerlukan jalur penyimpanan/penayangan rich text; tidak dinyatakan sebagai serangan anonim pada semua halaman.

**Perbaikan:** gunakan sanitizer server yang terpelihara atau perbaiki traversal sehingga seluruh descendant diperiksa; uji nested tag, atribut event, URL berbahaya, dan HTML malformed. Bersihkan konten lama setelah sanitizer benar. Kurangi `unsafe-inline`/`unsafe-eval` melalui nonce/hash dan refaktor skrip bertahap.

### S3 — P1/Tinggi: API publik tidak membatasi berita ke konten terbit

**Bukti:** `app/Controllers/ApiController.php:37,107–149` mengecualikan `news` dan `newsShow` dari autentikasi. `app/Models/News.php:173–194` memilih `n.*` tanpa filter status pada daftar. Detail memakai `find(id)` tanpa memeriksa status atau jadwal publikasi.

**Dampak:** draft dan konten yang belum semestinya dipublikasikan dapat keluar melalui `/api/news` dan `/api/news/{id}`, meskipun halaman berita biasa membatasi status. Daftar juga mengembalikan isi lengkap, yang meningkatkan ukuran respons.

**Validasi:** endpoint daftar terkonfirmasi dapat diakses tanpa login. Sampel lokal berisi lima berita berstatus published; tidak dibuat draft untuk pengujian. Kebocoran draft disimpulkan dari query dan guard, bukan dari pengambilan draft nyata.

**Perbaikan:** pisahkan endpoint admin dan publik. Endpoint publik harus memfilter `status = 'published' AND published_at <= NOW()` untuk daftar, detail, dan total pagination, serta memilih kolom yang diperlukan. Detail draft harus memberi 404 kepada anonim.

### S4 — P1/Tinggi: perubahan akun tidak segera mencabut sesi aktif

**Bukti:** `app/Controllers/Controller.php:768–811` menganggap login valid hanya karena `$_SESSION['user_id']` ada, dan mengembalikan role/izin dari salinan `$_SESSION['user']`. `ApiController.php:850–930` mengubah status, password, role, atau menghapus akun tanpa mekanisme revokasi sesi pengguna lain. Pemeriksaan `is_active` di `app/Models/User.php:93` dilakukan saat autentikasi.

**Dampak:** sesi yang telah login dapat terus memakai role/izin lama setelah akun dinonaktifkan, diturunkan haknya, dihapus, atau password direset. Regenerasi ID sesi berkala bukan revokasi akun. Tidak ditemukan pemeriksaan idle/absolute timeout aplikasi dalam jalur guard tersebut; masa hidup efektif juga bergantung konfigurasi sesi PHP.

**Validasi:** uji guard dengan sesi sintetis mengembalikan user/role admin tanpa lookup database. Ini bukan klaim bahwa klien dapat memalsukan session server dari luar.

**Perbaikan:** validasi akun aktif dan izin terkini pada request terlindungi, atau gunakan `session_version` yang dibandingkan dengan server. Naikkan versi saat perubahan kredensial/izin; tambahkan timeout server dan logout seluruh perangkat.

### S5 — P1/Tinggi: cek status SPMB dapat dienumerasi dan throttle mudah direset

**Bukti:** `app/Models/SPMBRegistration.php:70–80` menghasilkan nomor berbentuk tahun/bulan dan urutan `COUNT(*) + 1`. `app/Controllers/SPMBController.php:243–271` menerima nomor tersebut sebagai satu-satunya bukti akses. `views/frontend/spmb/status.php` menampilkan nama calon murid, asal sekolah, waktu daftar, status, dan catatan panitia.

`app/Controllers/Controller.php:816–835` menyimpan throttle publik dalam `$_SESSION`. Uji terisolasi dengan batas dua permintaan menghasilkan `[false,false,true]`; setelah sesi baru, hasil kembali `false`. Jadi batas 20 cek per 600 detik bukan pembatas global per IP. Header IP proxy juga diterima tanpa pemeriksaan trusted proxy. Nomor status disimpan di localStorage oleh halaman pendaftaran, yang kurang tepat jika nomor itu berfungsi sebagai satu-satunya kredensial pada komputer bersama.

**Dampak:** nomor berurutan dapat dicoba untuk melihat data pendaftar lain. Tidak dilakukan enumerasi data pendaftar nyata.

**Perbaikan:** gunakan token pelacakan acak terpisah atau verifikasi identitas/OTP; minimalkan data hasil pencarian dan pisahkan catatan internal dari pesan publik. Pindahkan throttle ke penyimpanan server bersama, dengan kunci IP/identitas dan kebijakan trusted proxy. Jangan mengandalkan CAPTCHA aritmetika atau nomor berurutan sebagai kontrol akses.

### S6 — P2/Sedang: throttle login mempercayai `CF-Connecting-IP` dari request

**Bukti:** `app/Controllers/Controller.php:942–954` membentuk file throttle dari username dan `HTTP_CF_CONNECTING_IP`, mendahului `REMOTE_ADDR`. Tidak ada pengecekan apakah koneksi berasal dari proxy tepercaya.

**Dampak bersyarat:** jika origin bisa diakses langsung dan server tidak membuang header tersebut, peminta dapat mengganti header untuk mendapat bucket login baru. Throttle login memang memakai file dan lock, sehingga reset cookie saja tidak menghapus bucket yang sama. CAPTCHA dalam sesi masih ada; celah ini melemahkan kontrol throttle, bukan membuktikan kompromi password.

**Perbaikan:** hanya percayai header proxy dari alamat proxy yang diizinkan; batasi akses langsung origin bila memakai Cloudflare. Terapkan batas per akun dan per IP secara terpisah. Bersihkan file throttle usang dengan kebijakan retensi.

### S7 — P2/Sedang: perlindungan data SPMB saat tersimpan belum setara kontak alumni

**Bukti:** `SPMBController.php:147–231`, `SPMBRegistration.php:14–47`, dan `database/schema.sql:428–471` menyimpan NIK, NISN, alamat, tanggal lahir, kontak orang tua, dan path dokumen tanpa enkripsi tingkat aplikasi. Kontak alumni sudah menggunakan `DataCipher::encrypt()` dengan AES-256-GCM. Tidak ditemukan persetujuan/pemberitahuan penggunaan data SPMB dalam form yang diperiksa maupun implementasi retensi dan restore otomatis di aplikasi.

**Dampak:** akses terhadap dump database atau salinan storage dapat membuka data pendaftaran. Ini bukan bukti disk/database hosting tidak dienkripsi dan bukan kesimpulan kepatuhan hukum. Backup hosting dan pengaturan produksi belum diperiksa.

**Perbaikan:** inventarisasi dan minimalkan data, batasi akses ekspor, gunakan enkripsi untuk data sensitif sesuai threat model, pisahkan kunci dari backup data, dan uji pemulihan keduanya. Tambahkan pemberitahuan penggunaan data, retensi, penghapusan terjadwal, serta audit akses/perubahan data sensitif. Jangan menghapus kunci alumni yang sedang digunakan.

### S8 — P2/Sedang: integritas dan validasi pendaftaran rentan saat gagal/bersamaan

**Bukti:** `SPMBRegistration.php:70–80` memakai `COUNT + 1`, sementara nomor memiliki unique constraint. Dua request paralel dapat menghasilkan nomor sama; menghapus record juga dapat menyebabkan nomor yang sudah ada terpilih lagi. Constraint mencegah duplikasi tersimpan, tetapi salah satu pendaftaran gagal.

`SPMBController.php:187–231` mengunggah dokumen sebelum validasi required fields dan insert, tanpa transaksi/cleanup file dalam jalur gagal. Validasi server pada blok tersebut terutama memeriksa nonkosong, belum format NIK/NISN/NPSN, rentang tanggal, enum, dan panjang seluruh field.

**Perbaikan:** gunakan sequence/ID atomik atau ID acak dengan retry, validasi semua data sebelum upload permanen, gunakan transaksi insert dan cleanup file yang gagal. Tambahkan idempotency untuk pengiriman ulang. Form perlu menunjukkan kesalahan per field dan mempertahankan isian.

## Kecepatan akses

Pengukuran berikut menggunakan `curl`, tiga GET berurutan per halaman, tanpa cookie autentikasi dan tanpa throttling jaringan. Angka mengukur respons HTML lokal saja, tidak termasuk waktu render, seluruh aset, pengguna konkuren, atau jaringan internet.

| Halaman | Median TTFB | Rentang TTFB | Ukuran body HTML |
| --- | ---: | ---: | ---: |
| Beranda | 161 ms | 130–187 ms | 58.908 byte |
| Berita | 139 ms | 105–145 ms | 45.361 byte |
| Galeri | 97 ms | 83–133 ms | 39.989 byte |
| Kontak | 105 ms | 104–129 ms | 37.771 byte |
| Login | 106 ms | 98–129 ms | 9.718 byte |

Semua 15 request memberi HTTP 200. Respons ini belum cukup untuk menyatakan Core Web Vitals lulus. Target pengujian produksi adalah LCP ≤2,5 detik, INP ≤200 ms, dan CLS ≤0,1 pada persentil ke-75, sesuai [Web Vitals](https://web.dev/articles/vitals).

### P1 — P2: file storage melewati bootstrap dan memegang lock sesi

`public/index.php:181–260` memulai sesi dan memeriksa instalasi sebelum streaming storage. Tidak ditemukan `session_write_close()` sebelum `readfile()`. Pada handler sesi berbasis file PHP, beberapa gambar/dokumen dalam sesi sama dapat antre menunggu lock; file besar juga memakai worker PHP selama transfer. Ini risiko konkurensi berdasarkan kode, belum load-test.

**Perbaikan:** aset publik dilayani web server/object storage; file privat melalui otorisasi lalu mekanisme transfer internal yang tepat. Tutup lock sesi setelah autentikasi/CSRF selesai dan sebelum streaming, dengan memastikan tidak ada penulisan sesi sesudahnya.

### P2 — P2: pemeriksaan instalasi, DDL, dan query berulang pada request publik

`isInstalled()` di `public/index.php:34–87` membuka koneksi dan memeriksa empat tabel, sepuluh kolom, serta tiga count jika tidak ada `config/local.php`/`APP_INSTALLED`. Fungsi dipanggil dua kali untuk request halaman biasa. Ini bersyarat; deployment dengan marker melewati pemeriksaan tersebut.

`app/Models/SiteVisit.php:24–54` menjalankan `CREATE TABLE IF NOT EXISTS` saat model pertama dibuat pada setiap request PHP; flag static hanya hidup selama request. Analitik juga melakukan insert sinkron. `SiteSetting::get/getAll` tidak memiliki cache request, sementara homepage, layout, dan maintenance guard memakai data setting yang berkaitan.

**Perbaikan:** jadikan migrasi/DDL proses instalasi atau deployment, simpan marker instalasi, cache setting/profile/menu dengan invalidasi saat perubahan, dan ukur jumlah/waktu query. Tentukan retensi analitik. Jangan meng-cache HTML berisi token CSRF atau sesi pengguna secara publik tanpa desain khusus.

### P3 — P2: `admin.js` memakai cache immutable setahun tanpa versi URL

**Bukti langsung:** `/js/admin.js` merespons `Cache-Control: public, max-age=31536000, immutable`, sedangkan `views/layouts/backend.php:616` memuat `/js/admin.js` tanpa hash atau query versi. Aset CSS dan beberapa skrip lain sudah menggunakan `filemtime`.

**Dampak:** sesudah update, browser lama dapat terus memakai JavaScript admin yang tidak cocok dengan backend; tombol/form dapat tampak rusak sampai cache kedaluwarsa/dibersihkan.

**Perbaikan:** terapkan versi konten/filemtime untuk semua aset immutable dan pastikan referensi berubah pada setiap rilis.

Catatan aset: CKEditor lokal berukuran 4.105.752 byte mentah dan dimuat pada form berita (`views/backend/news/form.php:10`). Ini bukan beban seluruh homepage. Ukur ukuran transfer terkompresi dan waktu parse pada perangkat lemah sebelum memutuskan pemangkasan plugin atau lazy loading. CSS terkompilasi, font lokal, cache aset, dan lazy loading pada sejumlah gambar sudah tersedia.

## UI/UX dan aksesibilitas

Browser diperiksa pada viewport desktop yang tersedia dan ponsel 390×844. Tema aktif Cendekia SMP. Beranda, menu ponsel, kontak, dan login diperiksa secara visual/DOM; menu ponsel berhasil dibuka dan navigasi ke kontak berjalan. Tidak ditemukan error/warning console pada sampel beranda. Halaman kontak tidak menunjukkan overflow horizontal pada ukuran tersebut. Ini bukan audit WCAG menyeluruh, dan dashboard setelah login belum diuji secara interaktif.

| Prioritas | Temuan dan bukti | Perbaikan |
| --- | --- | --- |
| P2 | `public/js/app.js:34–99` memblokir salin, pilih teks, Ctrl/Cmd+C/P/X, klik kanan, dan menampilkan overlay saat blur pada halaman dengan content protection. Status SPMB mengaktifkannya. | Hapus blokir interaksi dasar. Terapkan privasi di server; izinkan pendaftar menyalin nomor dan mencetak bukti. Proteksi ini tidak mencegah pengambilan data HTTP. |
| P2 | Checkbox `remember` ada di `views/auth/login.php:266`, tetapi `AuthController::handleLogin()` tidak memprosesnya. | Hapus opsi sampai tersedia atau implementasikan persistent login dengan token terpisah, rotasi, dan revokasi. |
| P2 | Tombol tampilkan password di `views/auth/login.php:218` tidak memiliki teks, `aria-label`, atau `title`; terkonfirmasi DOM browser. | Tambahkan nama aksesibel dinamis “Tampilkan/Sembunyikan password” dan status toggle yang sesuai. |
| P2 | Form SPMB memakai `alert()` untuk error umum dan potongan raw respons server saat gagal parse JSON, tanpa feedback field dari endpoint. | Beri ringkasan error yang mudah dipahami, pesan per field, fokus ke error, serta pengumuman status untuk pembaca layar. Hal positif: hirarki beranda dan CTA profil jelas, layout login terbaca pada ponsel, field login memiliki label dan autocomplete, serta tombol menu sudah memiliki nama aksesibel dan status expanded. Tidak ada alasan dari sampel ini untuk mengganti seluruh desain; perbaikan perilaku dan aksesibilitas lebih mendesak.

## Urutan tindak lanjut

1. Tutup bypass storage SPMB beserta cache publik; verifikasi izin admin/panitia pada endpoint unduh.
2. Perbaiki sanitizer dan audit rich text tersimpan; tambah regression test nested HTML.
3. Batasi API berita publik; terapkan revokasi sesi dan otorisasi terkini.
4. Ganti kredensial cek status yang mudah ditebak serta throttle per sesi/header proxy.
5. Perbaiki validasi/nomor registrasi/cleanup dokumen, lalu enkripsi-retensi-backup sesuai kebutuhan data.
6. Benahi lock sesi, query/DDL, versioning aset, dan UX yang teridentifikasi; ukur kembali di staging yang menyerupai produksi.

Validasi yang selesai: 111 file PHP lolos `php -l`; uji sanitizer dan guard/throttle terisolasi; uji HTTP file sintetis tanpa autentikasi beserta header dan body; 15 GET pengukuran halaman; pemeriksaan API daftar publik; pemeriksaan cache admin.js; pengujian browser desktop/ponsel. Kelulusan sintaks tidak berarti bebas celah keamanan.

Belum dilakukan: load test, Lighthouse/Core Web Vitals lengkap, validasi semua tema dan semua role lewat login, pemeriksaan konfigurasi TLS/WAF/DB produksi, audit CVE seluruh dependency, pemulihan backup, atau pemeriksaan kepatuhan hukum. Tidak ada klaim CMS telah diretas atau data nyata sudah bocor.

Acuan kontrol: [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), [OWASP XSS Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html), dan [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html). Acuan dipakai untuk saran kontrol; temuan proyek berasal dari kode dan pengujian lokal di atas.
